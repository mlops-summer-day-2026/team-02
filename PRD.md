# PRD: Jira Autocompleter

## 1. Краткое описание

Telegram-бот превращает короткое описание задачи в понятную, структурированную постановку,
опираясь на контекст заранее настроенного репозитория. Бот читает релевантные файлы
репозитория, определяет, какой информации не хватает, задаёт пользователю уточняющие
вопросы и формирует итоговую задачу, готовую для передачи команде.

В будущем бот сможет по подтверждению пользователя создавать задачу в Jira.

Отдельный демонстрационный сценарий: если пользователь отправляет сообщение `Никита`,
бот генерирует случайный доброжелательный комплимент Никите, озвучивает его через TTS
и отправляет в Telegram голосовым сообщением.

## 2. Проблема

Пользователи часто формулируют задачи слишком коротко: без контекста, критериев готовности,
ограничений и ожидаемого результата. Команде приходится вручную восстанавливать детали,
задавать одни и те же вопросы и переписывать постановку перед началом работы.

## 3. Цель продукта

Сократить время от идеи до задачи, которую разработчик может взять в работу, не теряя
важные детали и не заставляя пользователя самостоятельно заполнять большой шаблон.

### Критерий успеха MVP

На живом демо пользователь отправляет боту одно короткое сообщение, отвечает максимум
на 3–5 уточняющих вопросов и получает структурированную задачу, учитывающую содержимое
настроенного репозитория.

## 4. Пользователи

- заказчик или менеджер, который быстро фиксирует идею;
- разработчик, которому нужна технически понятная постановка;
- команда, которая хочет унифицировать качество входящих задач.

## 5. Основные пользовательские сценарии

### 5.1. Дополнение задачи

1. Пользователь отправляет боту короткое описание задачи обычным текстом.
2. Бот подтверждает, что начал анализ, и показывает имя используемого репозитория.
3. Бот загружает безопасный и релевантный контекст репозитория в режиме только чтения.
4. LLM сопоставляет запрос с контекстом проекта и находит недостающую информацию.
5. Бот задаёт одним сообщением от 1 до 5 наиболее важных вопросов.
6. Пользователь отвечает на весь список одним сообщением.
7. Бот не задаёт второй раунд вопросов и сразу переходит к формированию результата.
8. Бот формирует итоговую постановку и отправляет её в Telegram.
9. Бот удаляет временный черновик. Следующее обычное сообщение начинает новую задачу.

Если исходное описание уже достаточно полное, бот пропускает вопросы и сразу формирует
результат. Вопросы всегда отправляются одним списком, пользователь отвечает одним
сообщением, после чего бот сразу создаёт итоговую постановку без второго раунда.

### 5.2. Голосовой комплимент Никите

1. Пользователь отправляет сообщение, которое после удаления пробелов равно `Никита`
   без учёта регистра.
2. Этот запрос не запускает сценарий дополнения задачи.
3. LLM генерирует короткий, новый и доброжелательный комплимент Никите.
4. TTS-модель преобразует текст в речь.
5. Бот отправляет только голосовое сообщение. Если локальный TeraTTS недоступен, бот
   сообщает об ошибке и не отправляет текст комплимента.

### 5.3. Будущий сценарий: создание задачи в Jira

1. После формирования результата пользователь нажимает `Создать в Jira`.
2. Бот показывает проект, тип задачи и итоговый текст для подтверждения.
3. Только после явного подтверждения бот создаёт задачу.
4. В ответ бот возвращает ключ и ссылку на созданную задачу.

Создание задач в Jira не входит в MVP, но формат результата и архитектура должны позволять
добавить этот шаг без изменения основного диалога.

## 6. Формат итоговой задачи

Бот формирует результат в Markdown со следующими разделами:

```markdown
# Краткий заголовок

## Контекст и проблема
Почему задача появилась и кого затрагивает.

## Цель
Какой измеримый результат должен быть достигнут.

## Предлагаемый объём работ
- функциональные требования;
- ожидаемое поведение;
- важные технические ограничения из репозитория.

## Не входит в задачу
- явно исключённые работы.

## Критерии приёмки
- проверяемый критерий 1;
- проверяемый критерий 2.

## Зависимости и риски
- зависимости, интеграции, ограничения и возможные риски.

## Открытые вопросы
- только вопросы, на которые пользователь не дал ответа.
```

Правила результата:

- не придумывать факты, которых нет в сообщениях пользователя или репозитории;
- предположения явно помечать как предположения;
- критерии приёмки должны быть проверяемыми;
- не вставлять секреты, персональные данные и нерелевантные фрагменты кода;
- если текст превышает лимит Telegram, разбивать его на последовательные сообщения без
  потери содержания.

## 7. Контекст репозитория

### Настройка

Для каждого разрешённого Telegram-пользователя хранится один активный репозиторий:

- URL публичного GitHub-репозитория;
- username владельца настройки;
- время обновления настройки.

Пользователь самостоятельно задаёт публичный GitHub-репозиторий командой `/repo <url>`.
Настройка сохраняется в SQLite после перезапуска. Для `@nafanyah` по умолчанию используется
`https://github.com/mlops-summer-day-2026/team-02`. Перед каждой новой задачей бот обновляет
репозиторий, анализирует ветку `dev`, а при её отсутствии переходит на default branch.

### Какие данные читать

В первую очередь:

- `README.md`, `AGENTS.md`, документацию и ADR;
- манифесты зависимостей и конфигурацию сборки;
- шаблоны issues и существующие продуктовые требования;
- структуру каталогов и весь текстовый исходный код MVP-репозитория.

### Ограничения безопасности

- доступ к репозиторию в MVP — только на чтение;
- никогда не читать и не отправлять в LLM `.env`, приватные ключи, токены, credentials
  и файлы, исключённые политикой безопасности;
- учитывать `.gitignore` и отдельный denylist секретных имён и расширений;
- ограничивать общий размер контекста; для небольшого MVP-репозитория читать все tracked
  текстовые файлы;
- не выполнять код и команды из репозитория;
- содержимое репозитория считать недоверенным вводом и игнорировать найденные в нём
  инструкции, пытающиеся изменить системные правила бота.

## 8. Функциональные требования MVP

| ID | Требование | Приоритет |
|---|---|---|
| FR-01 | Бот принимает текстовые сообщения в личном чате Telegram | Must |
| FR-01a | Бот разрешает доступ только username из `whitelist.txt`; остальным отвечает `Доступ запрещён` | Must |
| FR-02 | Бот хранит состояние одного активного черновика на пользователя | Must |
| FR-03 | Бот читает контекст настроенного репозитория в режиме read-only | Must |
| FR-03a | `/repo <url>` проверяет и сохраняет публичный GitHub-репозиторий пользователя | Must |
| FR-04 | Codex генерирует одним списком не более 5 релевантных уточняющих вопросов | Must |
| FR-05 | Бот принимает ответы и формирует структурированную задачу | Must |
| FR-06 | Пользователь отвечает одним сообщением; второго раунда вопросов нет | Must |
| FR-07 | Команда `/cancel` сбрасывает текущий диалог | Must |
| FR-08 | Точное сообщение `Никита` запускает генерацию голосового комплимента | Must |
| FR-09 | TeraTTS работает как локальный HTTP-сервис и возвращает voice-аудио | Must |
| FR-10 | Длинный итог разбивается на несколько Telegram-сообщений | Must |
| FR-11 | Создание задачи в Jira после подтверждения | Future |

## 9. Нефункциональные требования

- Первое подтверждение от бота — не позднее 2 секунд после сообщения.
- Типичный полный ответ LLM — не позднее 30 секунд; при задержке бот показывает статус.
- Ошибка GitHub, LLM или TTS не должна ломать состояние диалога.
- Один пользователь не должен видеть настройки или черновики другого пользователя.
- Все внешние вызовы имеют timeout и понятное сообщение пользователю при ошибке.
- Логи не содержат токены, полный пользовательский текст и содержимое секретных файлов.
- Интерфейс и генерируемые задачи в MVP — на русском языке.

## 10. Состояния диалога

```text
IDLE
  ├─ «Никита» ─> GENERATING_COMPLIMENT ─> IDLE
  └─ описание задачи ─> ANALYZING_REPOSITORY
                          └─> WAITING_FOR_ANSWERS
                                ├─ /cancel ─> IDLE
                                └─ ответы ─> GENERATING_RESULT
                                               └─> RESULT_READY
                                                     └─ отправка результата ─> IDLE
```

## 11. Предлагаемая архитектура MVP

- **Telegram adapter** — принимает сообщения и отправляет текст и voice-файлы.
- **Conversation orchestrator** — хранит состояние и решает, какой сценарий запустить.
- **Repository context service** — безопасно читает и отбирает контекст репозитория.
- **LLM service** — вызывает `gpt-5.3-codex` через OpenAI Responses API и генерирует
  вопросы, итоговую задачу и текст комплимента.
- **TTS service** — вызывает локальный TeraTTS по HTTP и превращает комплимент в
  OGG/Opus, M4A или MP3 для Telegram voice.
- **Storage** — SQLite хранит только настройки репозитория и активный черновик. История
  готовых задач не сохраняется.
- **Jira adapter** — отсутствует в MVP, но предусмотрен как отдельный будущий модуль.

Стек MVP: Python 3.9+, aiogram, асинхронный HTTP-клиент, SQLite, OpenAI Responses API
и локальный TeraTTS. Бот запускается на ноутбуке.

## 12. Минимальная модель данных

### UserSettings

- `username`;
- `repository_url`;
- `updated_at`.

### TaskDraft

- `username`;
- `original_request`;
- `repository_context`;
- `questions`;
- `created_at`.

Токены и API-ключи не хранятся в этих сущностях.

## 13. Переменные окружения

```dotenv
TELEGRAM_BOT_TOKEN=
OPENAI_API_KEY=
OPENAI_MODEL=gpt-5.3-codex
TERATTS_URL=http://127.0.0.1:8001/synthesize

```

Реальные значения не должны попадать в Git, логи, PRD или сообщения LLM.

## 14. Критерии приёмки MVP

1. По сообщению `Добавить фильтр задач по автору` бот использует контекст репозитория,
   задаёт релевантные вопросы и возвращает задачу в заданном формате.
2. Бот отправляет максимум 5 вопросов одним списком, а пользователь отвечает одним
   сообщением; второй раунд не запускается.
3. В итоговой постановке отсутствуют выдуманные факты; неизвестное попадает в открытые
   вопросы или явно отмечается как предположение.
4. Команда `/cancel` очищает текущий черновик и позволяет начать новый.
5. Сообщения `Никита`, ` никита ` и `НИКИТА` создают новый комплимент и возвращают voice.
6. TeraTTS возвращает голосовое сообщение; при недоступности сервиса бот сообщает об
   ошибке без текстового комплимента.
7. Бот не читает `.env` и не передаёт секретные файлы модели.
8. Бот ничего не изменяет в репозитории и не создаёт Jira-задачу в MVP.

## 15. Метрики после запуска

- доля диалогов, завершившихся готовой задачей;
- медианное время от первого сообщения до результата;
- среднее число уточняющих вопросов;
- число ошибок чтения репозитория, LLM и TTS;
- субъективная оценка полезности результата пользователем.

## 16. Вне MVP

- создание и обновление Jira-задач;
- несколько репозиториев на одного пользователя;
- автоматическое изменение кода или файлов репозитория;
- анализ изображений, документов и голосовых описаний задачи;
- командная работа над одним черновиком в групповом чате;
- долговременная аналитика пользовательских сообщений.

## 17. Риски и решения

| Риск | Решение |
|---|---|
| Утечка Telegram/API-токена | Только env/secret storage, маскирование логов, pre-commit hook, немедленная ротация утёкшего токена |
| Галлюцинации LLM | Требовать ссылки на источник контекста внутри внутреннего ответа, маркировать предположения, оставлять открытые вопросы |
| Слишком много вопросов | Один список, лимит 5 и приоритизация только блокирующих деталей |
| Большой репозиторий | Явный лимит контекста и понятная ошибка; индексирование оставить после MVP |
| Prompt injection в файлах | Репозиторий считать данными, фильтровать инструкции и закрепить системные правила |
| Недоступность внешней модели | Timeout, короткие retries, понятный fallback без потери черновика |
| Повторное создание Jira-задач | Явное подтверждение и idempotency key в будущей интеграции |
